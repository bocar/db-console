# 国产化与离线环境交付采用随包 JDK 17，不建 JDK 8 降级分支

目标环境调研确认三类现场：信创环境（麒麟 V10 + 鲲鹏/飞腾/海光/兆芯，预装毕昇 JDK 8）、存量 CentOS + JDK 8 环境、Debian 系（含 Ubuntu）+ JDK 8 环境，且均无系统级安装 JDK 17 的通道。曾有提议将应用降级到 JDK 8 以直接复用现场 Java。裁决：**维持 Spring Boot 3.4 / Java 17 主线不动，交付物改为「fat JAR + 随包国产 JDK 17」的 Linux 离线包**（`packaging/package.sh` 产出，解压即用、不写入系统路径），不为 JDK 8 建立 Boot 2.7 降级分支。

理由：

1. **JDK 17 在这些现场技术上全部可达**。毕昇 JDK 本身只发布 aarch64 / x86_64——预装毕昇 8 即证明 CPU 属于这两族；麒麟 V10 SP1+ 与 CentOS 7+（glibc ≥ 2.17）均在毕昇/Kona/Dragonwell JDK 17 的支持矩阵内。仅 CentOS 6（glibc 2.12）与龙芯 MIPS、申威 SW64 真正缺 JDK 17，属边缘站点，不为其预置工程复杂度。
2. **降级分支的代价是不对称的**。Spring Boot 2.7 OSS 支持已于 2023-11 结束，2026 年起零 CVE 补丁；本应用持有数据库凭据、执行写操作、落审计日志，跑无补丁框架与自身的安全基线（确认机制、凭据隔离）相悖。工程上还需改造约 34 处 record、33 处 jakarta→javax 及若干 API 差异（个位数人天），并永久维护一条双主线。
3. **「无法安装」的约束形态支持随包解法**。两轮沟通确认限制在"不装系统级 JDK"（无安装通道/口径），而非"应用目录不得自带运行时"。随包 JDK 与现有 JDK 8 共存，不触碰系统路径，合规叙事顺滑（信创现场随包的仍是国产毕昇，仅版本不同）。
4. **交付面收敛在打包层**。`packaging/` 脚本按 `uname -m` 选 aarch64/x64 构建，`start.sh` 的 JDK 解析只有两条路径（显式 `DB_CONSOLE_JAVA_HOME` → 随包），**不探测系统 java**——现场预装的毕昇 JDK 8 完全不参与运行；status/stop/restart 覆盖裸进程与 systemd 两种形态；产物名 `-linux-<arch>` 与具体发行版解耦，对麒麟、CentOS、Debian 系通用，x64 无信创要求时亦可用 Eclipse Temurin 17。

## Consequences

- 主线继续留在受支持的 Spring Boot 3.x，升级与安全修复单轨推进；
- 每个新站点组合需按 packaging/README.md 的适配记录表做一次真机验证（start/登录/双库查询/停止），作为信创适配报告底稿；
- 若未来出现「整机锁死仅允许 JDK 8、随包亦不允许」的硬口径站点，本 ADR 的重评门槛被触发，届时再评估降级分支——按第 2 条代价，倾向要求站点先放开随包 JDK。

## 重评触发器（任一满足即重开评估）

- 出现成规模且无法接受随包 JDK 17 的目标站点（CentOS 6 / JDK 8 硬口径）；
- 信创主管部门口径变化，明确禁止应用目录携带运行时。
